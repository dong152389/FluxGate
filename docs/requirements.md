# VPN 订阅聚合器需求说明

## 1. 项目目标

做一个尽量偏纯前端的 VPN 订阅聚合项目，允许用户在管理页面中配置多个上游订阅链接，将多个订阅中的节点聚合、重命名、去重后，对外提供一个新的可长期访问的聚合订阅链接。

项目需要带基础用户系统，用于保护用户配置、隔离不同用户的数据，降低订阅链接泄漏风险。

## 2. 目标用户

- 自己管理多个订阅源的个人用户
- 希望将多个机场节点合并成一个统一订阅入口的用户
- 希望对节点名称进行统一整理、加前缀、手动改名的用户
- 需要登录后管理自己私有订阅配置、避免他人查看的用户

## 3. 范围结论

为了生成“真正可访问的新订阅链接”，项目采用：

- 前端：静态管理页面
- 后端：Cloudflare Worker 作为最小聚合服务
- 存储：Cloudflare D1 保存用户、配置、订阅源、重命名映射；Cloudflare KV 保存缓存

不采用纯浏览器直连的原因：

- 浏览器请求第三方订阅源容易遇到 CORS 限制
- 纯前端页面无法稳定对外提供一个新的订阅 URL 给客户端长期拉取
- 上游订阅链接属于敏感信息，不适合暴露在公开静态页面中

## 4. 核心使用流程

1. 用户注册或登录管理页面
2. 用户添加多个上游订阅链接，并填写来源名称
3. 用户保存自己的聚合配置
4. 页面展示每个订阅源的拉取状态、节点数量、错误信息
5. 页面展示聚合后的节点预览
6. 用户可对节点做重命名处理
7. 系统为当前用户生成一个新的聚合订阅链接
8. Clash / Mihomo / sing-box 等客户端使用该聚合订阅链接拉取节点

## 5. 输入与输出

### 输入

- 多个订阅源 URL
- 每个订阅源的显示名称
- 是否启用该订阅源
- 节点重命名规则
- 去重规则
- 用户账号信息

### 输出

- 一个新的聚合订阅链接
- 可选的聚合结果文本预览
- 每个源的状态信息与日志摘要
- 当前用户自己的配置数据和安全设置

## 5.1 用户系统目标

用户系统的目的不是做复杂社交平台，而是控制访问和做数据隔离。

首版目标：

- 用户可注册
- 用户可登录 / 登出
- 每个用户只能看到和修改自己的订阅源、规则、别名、公开订阅 token
- 公开订阅链接与管理端登录态分离
- 用户可以主动重置自己的公开订阅 token

不把“用户系统”理解成仅有一个总后台管理员。
首版推荐做成轻量多用户模型，即每个账号拥有自己的独立聚合空间。

## 6. 首版支持的订阅格式

首版支持：

- 明文多行订阅内容，例如每行一个 `vless://...`、`vmess://...`
- Base64 编码的订阅文本，解码后再按多行 URI 处理

首版默认协议支持策略：

- 明确支持 `vmess://`
- 明确支持 `vless://`
- 对其他 `://` 形式的节点字符串保留兼容入口，但不承诺首版做完整字段级改名

## 7. 节点解析与命名规则

### 7.1 节点名称提取

- `vless://` 通过 URL fragment 提取节点名，例如 `#香港01`
- `vmess://` 解码 JSON 后使用 `ps` 字段作为节点名
- 如果节点没有名称，则使用协议 + 主机名生成兜底名称

### 7.2 节点重命名能力

首版默认同时支持两种方式：

- 批量规则改名
- 单节点手动改名

批量规则改名包括：

- 添加来源前缀，例如 `[机场A]`
- 添加统一前缀或后缀
- 文本替换
- 正则替换

单节点手动改名包括：

- 在预览列表中直接编辑节点名称
- 基于节点指纹持久化保存别名
- 后续重新拉取订阅时，若节点指纹不变，则继续应用已保存的别名

节点指纹建议基于以下字段生成稳定哈希：

- 协议
- 服务端地址
- 端口
- 用户标识或等价唯一字段

## 8. 去重规则

首版默认启用去重。

去重策略：

- 对可结构化解析的节点，按协议 + 服务器 + 端口 + 用户标识生成指纹去重
- 对无法完整结构化解析的节点，按原始 URI 归一化后计算哈希去重

去重冲突保留策略：

- 默认保留第一个启用源中的节点
- 被去重节点在预览中可标记来源，便于后续排查

## 9. 管理端功能

### 9.1 订阅源管理

- 新增订阅源
- 编辑订阅源
- 删除订阅源
- 启用 / 禁用订阅源
- 调整订阅源优先级
- 测试拉取订阅源

每个订阅源字段：

- `id`
- `userId`
- `name`
- `url`
- `enabled`
- `priority`
- `notes`

说明：

- `url` 是产品层字段
- 持久化时建议只存加密后的 `urlEncrypted`

### 9.2 聚合规则管理

- 是否去重
- 来源名前缀模板
- 批量重命名规则
- 是否保留无名称节点
- 节点排序方式

### 9.3 节点预览

- 展示解析后的节点列表
- 展示节点来源
- 展示原始名称与新名称
- 支持搜索与筛选
- 支持单节点编辑名称

### 9.4 订阅发布

- 生成聚合订阅链接
- 复制订阅链接
- 预览原始输出内容
- 触发刷新缓存
- 重置公开订阅 token

### 9.5 用户系统

- 注册
- 登录
- 登出
- 查看当前账号信息
- 修改密码
- 重置公开订阅 token

首版可选但建议预留：

- 忘记密码
- 邮箱验证
- 管理员禁用账号

## 10. 对外订阅链接行为

推荐对外发布形式：

- `https://your-domain.com/sub/{token}`

访问该链接时，Worker 执行：

1. 根据 `token` 找到所属用户
2. 读取该用户的聚合配置
3. 拉取所有启用的上游订阅
4. 解析节点
5. 应用去重和改名规则
6. 重新序列化为订阅内容
7. 按订阅客户端兼容方式输出

输出策略：

- 默认输出为 Base64 编码订阅文本
- 可选提供 `?raw=1` 返回明文多行 URI

## 11. 缓存策略

为了避免每次访问都实时拉取所有上游源，首版建议加入缓存。

缓存建议：

- Worker 侧缓存聚合结果 5 到 15 分钟
- 管理端支持手动刷新
- 某个源拉取失败时，可配置是否继续使用上次成功缓存

默认行为建议：

- 某一源失败不阻塞整体输出
- 返回结果中忽略失败源
- 失败信息写入管理端状态页

## 12. 安全与权限

管理端必须与公开订阅链接分离。
用户之间也必须强隔离。

首版安全方案建议：

- 用户密码使用强哈希存储，例如 `argon2` 或 `scrypt`
- 管理端使用会话 Cookie 或 JWT 鉴权
- 所有管理端接口按 `userId` 做严格隔离
- 公开订阅链接使用每个用户独立的随机 token 访问
- 用户可随时重置自己的公开 token，旧 token 立即失效
- 上游订阅 URL 仅存储在 Worker 绑定存储中，不下发到其他用户或公开页面
- 上游订阅 URL 建议用应用级密钥加密后再落库，降低存储泄漏风险

需要明确的边界：

- 用户系统可以显著降低“他人看到我的订阅配置”的风险
- 但只要服务端需要代拉上游订阅，就意味着服务端在运行时必须能拿到明文 URL
- 因此该方案不是零知识架构，平台运维者理论上仍具备访问能力

后续可升级：

- Cloudflare Access
- GitHub OAuth 登录
- 多用户配置隔离
- 审计日志
- 二步验证

## 13. 首版 MVP 范围

MVP 必做：

- 静态管理页面
- Cloudflare Worker 聚合接口
- 用户注册 / 登录 / 登出
- 用户级数据隔离
- 多订阅源配置
- 明文 + Base64 订阅解析
- `vmess` / `vless` 名称提取与重写
- 去重
- 批量重命名
- 单节点改名
- 新订阅链接生成
- 缓存
- 管理端鉴权

MVP 不做：

- 流量统计
- 节点测速
- 自动探活
- 复杂分组策略
- 完整邮件找回密码链路
- OAuth 第三方登录

## 14. 推荐技术方案

前端建议：

- React + Vite
- Tailwind CSS 或简单 CSS Modules
- Zustand 管理本地 UI 状态

后端建议：

- Cloudflare Worker
- Cloudflare D1 存用户、配置、源地址、别名、token 映射
- Cloudflare KV 存聚合缓存
- Worker Secret 存 URL 加密密钥、JWT 密钥或会话签名密钥

接口建议：

- `POST /api/auth/register`
- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/auth/me`
- `POST /api/auth/change-password`
- `POST /api/auth/reset-public-token`
- `GET /api/config`
- `PUT /api/config`
- `POST /api/test-source`
- `GET /api/preview`
- `POST /api/rename-node`
- `POST /api/refresh`
- `GET /sub/:token`

鉴权建议：

- 浏览器管理端优先用 HttpOnly Cookie 会话
- 若需要纯 API 客户端，再补 Bearer Token

## 15. 数据模型草案

### User

- `id: string`
- `email?: string`
- `username: string`
- `passwordHash: string`
- `status: active | disabled`
- `createdAt: string`
- `updatedAt: string`

### SubscriptionSource

- `id: string`
- `userId: string`
- `name: string`
- `urlEncrypted: string`
- `enabled: boolean`
- `priority: number`
- `notes?: string`

### RenameRule

- `userId: string`
- `id: string`
- `type: prefix | suffix | replace | regex`
- `enabled: boolean`
- `match?: string`
- `replace?: string`
- `value?: string`
- `order: number`

### NodeAlias

- `userId: string`
- `fingerprint: string`
- `alias: string`
- `updatedAt: string`

### AggregationConfig

- `userId: string`
- `publicToken: string`
- `dedupeEnabled: boolean`
- `prefixSourceName: boolean`
- `renameRules: RenameRule[]`
- `sources: SubscriptionSource[]`

### Session

- `id: string`
- `userId: string`
- `expiresAt: string`
- `createdAt: string`
- `lastSeenAt: string`

## 16. 非功能要求

- 管理端在移动端和桌面端都可用
- 聚合结果尽量在 2 到 5 秒内返回
- 某个源失败时整体服务尽量可用
- 输出格式尽量兼容主流订阅客户端
- 配置变更后能即时生效或手动刷新生效
- 用户之间的数据不能互相读取
- 公开 token 重置后旧链接必须失效
- 用户敏感配置不能在前端明文持久化到公开静态资源中

## 17. 已确认决策

- 需要一个真正可访问的新订阅链接
- 需要支持 Base64 订阅输入
- 需要节点去重
- 需要节点重命名
- 需要基础用户系统
- 部署方式采用 静态前端 + Cloudflare Worker

## 18. 当前默认假设

如果没有进一步补充，后续实现按以下假设推进：

- 轻量多用户场景
- 首版重点兼容 `vmess` 和 `vless`
- 聚合输出默认提供 Base64 订阅
- 节点改名同时支持批量规则和单节点别名
- 源拉取失败时不影响其他源聚合
- 登录方式首版采用用户名密码
- 每个用户只有一个默认聚合空间和一个公开订阅 token
